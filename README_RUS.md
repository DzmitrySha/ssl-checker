# SSL Checker

Утилита для проверки срока действия TLS-сертификатов узлов: подключение по TLS, чтение сертификата, расчёт оставшихся **календарных** дней до даты окончания, опциональные уведомления (Windows и корпоративный HTTP API), пакетные отчёты и режим ежедневного расписания. В корпоративный API **по умолчанию** ничего не уходит, если по всем узлам полный «ОК»; сообщение — только при поводах (просрочка и пороги предупреждений, ошибка проверки, проблема цепочки доверия) или при принудительном **`--notify-always`** (см. ниже). Запуск в контейнере на Linux описан в разделе [Docker на Linux](#docker-на-linux).

Точка входа: `main.py` и консольная команда **`ssl-checker`** (см. `[project.scripts]` в `pyproject.toml`).

## Возможности

| Область | Описание |
|--------|----------|
| **TLS** | Подключение к хосту:порту, таймаут 10 с; проверка цепочки доверия по настройкам `TLS_*` в `.env`. |
| **Срок** | Даты `notBefore` / `notAfter`, оставшиеся календарные дни; при частичном сбое проверки цепочки опционально чтение только срока с сертификата (`TLS_READ_EXPIRY_ON_VERIFY_FAIL`). |
| **Список узлов** | `SITES_TO_CHECK` в `.env` и/или файл `SITES_FILE` (приоритет у файла, если он существует); формат `хост` или `хост:порт`. |
| **Разовая проверка** | Один узел (`--site`) или весь список из `.env` без `--site`. |
| **JSON** | Флаг `--json`: результат в stdout одним объектом или массивом. |
| **Пакет (`--batch`)** | Все узлы, сводный Markdown-отчёт в **лог всегда**; в корпоративный HTTP API при настроенном сервисе — **только при поводе** по хотя бы одному узлу (просрочка или окончание в день проверки, срок ниже `WARN_DAYS` / `CRITICAL_DAYS`, ошибка TLS/сети, неподтверждённая цепочка доверия). При полном «ОК» по списку в API **ничего не отправляется**, если не задан флаг **`--notify-always`** (тогда уходит полный отчёт, в т.ч. для отладки канала). Код выхода `1`, если хотя бы один узел **требует внимания** (те же условия, что для API), иначе `0`. |
| **Планировщик (`--schedule`)** | Долгоживущий процесс: ежедневный cron + опционально первая пакетная проверка при старте; правила удалённого API **как у `--batch`**, флага **`--notify-always` здесь нет** — принудительно «всё ОК» в API не отправить. Типичный сценарий в контейнере — см. [Docker на Linux](#docker-на-linux). |
| **Уведомления Windows** | Окно/сообщение при ошибке проверки, просрочке/порогах `WARN_DAYS` / `CRITICAL_DAYS`, предупреждении по цепочке (`SEND_WIN_ALERT`, `WIN_USE_NATIVE_MSGBOX`). |
| **Корпоративный API** | `POST {NOTIFICATION_API_BASE_URL}/api/v1/notifications` при полной настройке в `.env` (`SEND_NOTIFICATIONS` и связанные переменные). |
| **Логи** | Loguru, каталог `./logs` или `LOGS_DIR` из `.env`. |

Логика проверки: `core/ssl_cert_monitor.py`; пакет и отчёт: `core/batch_report.py`; правила статусов и порогов: `core/status_policy.py`; тексты ошибок для отчёта и UI: `core/error_messages.py`; настройки: `config/settings.py`.

## Требования

- Python **3.12+**
- Рекомендуется **[uv](https://docs.astral.sh/uv/)** для разработки и запуска из исходников.

Параметры читаются через `python-dotenv`. Рабочий каталог процесса должен содержать файл `.env` (или переменные окружения заданы иначе).

## CLI: команда `ssl-checker`

После `uv sync` запуск из корня проекта:

```bash
uv run ssl-checker --help
```

Эквивалент:

```bash
uv run python main.py --help
```

### Аргументы

| Аргумент | Описание |
|----------|----------|
| `--site HOST_OR_URL` | Один хост или URL (с портом в URL, если нужен нестандартный). **Без** `--site` проверяется весь список из `SITES_TO_CHECK` / `SITES_FILE`. |
| `--port N` | Порт TLS, если в `--site` нет порта (по умолчанию из `.env`: `SITE_PORT`, обычно 443). |
| `--json` | Вывести результат в **stdout** в JSON (один объект для одного узла, массив — для нескольких). Без `--json` — человекочитаемый вывод в лог и диалоги/уведомления по правилам приложения. |
| `--notify-always` | Принудительно отправить уведомление в корпоративный API/Mattermost **даже если всё в порядке** (отладка канала). С **`--batch`** — полный сводный отчёт; при разовой проверке без `--batch` — сообщение в API и при «зелёном» сертификате (окно Windows при полном ОК не показывается). **Несовместим** с `--schedule`. |
| `--batch` | Один прогон: все узлы из списка, сводный отчёт в лог; в API — только при **поводах** по узлам (см. [Уведомления в API / Mattermost](#уведомления-в-api--mattermost)), если не задан **`--notify-always`**. **Несовместим** с `--site`. Код выхода: `0` — по всем узлам без замечаний (срок и цепочка), `1` — хотя бы один узел требует внимания (просрочка, пороги, цепочка, ошибка TLS/сети и т.д.). |
| `--lang EN\|RU` | Язык интерфейса (по умолчанию из `LANGUAGE` в `.env` или `ru`). |
| `--schedule` | Планировщик: каждый день в время из `.env`, опционально пакет при старте. **Несовместим** с `--site`, `--json` и `--notify-always`. |

Режимы `--batch` и `--schedule` взаимно исключают друг друга (группа в `argparse`).

### Примеры CLI

```bash
uv run ssl-checker
uv run ssl-checker --site ias.energo.net --port 443
uv run ssl-checker --site https://example.com:8443 --json
uv run ssl-checker --json
uv run ssl-checker --batch
uv run ssl-checker --batch --notify-always
uv run ssl-checker --schedule
```

- Без `--site`: читается список из `.env`; если после разбора токенов список **пуст** (`SITES_TO_CHECK` пуст и файл `SITES_FILE` отсутствует/пуст) — программа завершится с ошибкой; задайте хотя бы один узел (см. `.env.example`).
- С `--site`: список из `.env` для этого запуска **не** подмешивается — проверяется только указанный узел (после нормализации URL/хоста).

### Уведомления в API / Mattermost

При `SEND_NOTIFICATIONS=true` и полном наборе полей API логика такая: **«тихий» успех в API не шлётся** — запрос уходит только если есть **повод** по узлу **или** включён принудительный режим (где он поддерживается).

**Повод для удалённого уведомления** (тот же смысл, что и для окон/статусов в `core/status_policy.py`):

- просрочка или срок **0** календарных дней (истекает в день проверки);
- срок в зоне критического или предупреждающего порога: меньше `CRITICAL_DAYS` или меньше `WARN_DAYS` (см. `.env`);
- **ошибка** проверки узла (TLS, сеть, не удалось прочитать сертификат и т.п.);
- срок ещё «зелёный», но **цепочка доверия** к издателю не подтверждена.

Дальше по режимам:

- **Разовая проверка** (без `--batch`): для каждого узла из прогона сообщение в API уходит **только при поводе** из списка выше; при полностью «зелёном» сертификате в API **ничего не отправляется** (только лог). Флаг **`--notify-always`** добавляет отправку и при полном ОК (окно Windows при чистом ОК по-прежнему не показывается).
- **`--batch`**: сводка в лог всегда; в API — **только если есть хотя бы один узел с поводом**, иначе тишина. **`--batch --notify-always`** — один принудительный отчёт в API даже при полном ОК по всем узлам.
- **`--schedule`**: как **`--batch`** по правилам API, но **`--notify-always` недоступен** — в расписании нельзя запросить уведомление «на всякий случай» при полном ОК.

### Глобальная команда `ssl-checker` в системе

Чтобы в любом каталоге работало `ssl-checker --help`:

1. **[pipx](https://pipx.pypa.io/)** (изолированная установка в PATH):

   ```bash
   pipx install /path/to/ssl_checker
   ```

2. **[uv tool](https://docs.astral.sh/uv/guides/tools/)**:

   ```bash
   uv tool install /path/to/ssl_checker
   ```

3. Добавить в **PATH** каталог `bin` / `Scripts` виртуального окружения проекта (например `.../ssl_checker/.venv/bin` на Linux или `...\ssl_checker\.venv\Scripts` в Windows) после `uv sync`.

Во всех случаях убедитесь, что при запуске процесс «видит» нужный `.env` (запуск из каталога с `.env` или заранее выставленные переменные среды).

## Ежедневный запуск в Windows без Docker

Один раз в сутки по Планировщику заданий достаточно вызвать пакетную проверку, без долгоживущего процесса.

1. Настройте `.env`: список сайтов, при необходимости `SEND_NOTIFICATIONS` и поля API.
2. **Планировщик заданий** → создать задачу → триггер «ежедневно».
3. Действие: `cmd.exe` с `/c` и путём к `scripts\run_daily.cmd`.
4. Рабочая папка: корень проекта (где `.env` и `pyproject.toml`).

`run_daily.cmd` вызывает `uv run python main.py --batch` (в API — только при поводах по узлам или с **`--notify-always`**). Для проверки канала на «зелёном» списке временно добавьте **`--notify-always`** к `--batch`. В **`--schedule`** (Docker) принудительной отправки при полном ОК нет. Для долгоживущего планировщика в контейнере на Linux см. [Docker на Linux](#docker-на-linux).

## Сервис уведомлений (HTTP)

Запрос: `POST {NOTIFICATION_API_BASE_URL}/api/v1/notifications` с телом JSON (`title`, `text`, `deliverToMattermost`, `userSids`) и заголовками **`clientSecretKey`**, **`appLabel`**. Поле `link` клиент **не отправляет** (чтобы в Mattermost не появлялась пустая ссылка).

Минимально для отправки: `SEND_NOTIFICATIONS=true`, заданы URL, ключ, лейбл и **хотя бы один** идентификатор в `NOTIFICATION_USER_IDS`. Флаг `deliverToMattermost` в JSON задаётся переменной **`NOTIFICATION_DELIVER_TO_MATTERMOST`** (по умолчанию `true`).

`NOTIFICATION_API_TLS_VERIFY` — проверка TLS при исходящем POST: `true` / `false` / путь к PEM корневого сертификата издателя.

## Основные переменные `.env`

| Переменная | Назначение |
|------------|------------|
| `SITE_PORT` | Порт TLS по умолчанию для узлов без `:порт`. |
| `LOGS_DIR` | Каталог логов; пусто — `./logs` рядом с проектом. |
| `SITES_TO_CHECK`, `SITES_FILE` | Список узлов для обычного запуска и `--batch`. |
| `WARN_DAYS`, `CRITICAL_DAYS` | Пороги предупреждений (календарные дни). |
| `SEND_WIN_ALERT`, `WIN_USE_NATIVE_MSGBOX` | Окна Windows. |
| `SEND_NOTIFICATIONS`, `NOTIFICATION_*` | Корпоративный API уведомлений; отдельно: `NOTIFICATION_DELIVER_TO_MATTERMOST` — доставка в Mattermost. |
| `TLS_VERIFY` | `true` / `false` / путь к PEM: доверие к цепочке узла. |
| `TLS_SITE_CHECK_TRUST_ONLY_CAFILE` | Только PEM из `TLS_VERIFY`, без системного хранилища. |
| `TLS_READ_EXPIRY_ON_VERIFY_FAIL` | После ошибки verify повтор без проверки и чтение только срока. |
| `SCHEDULER_TIMEZONE` | IANA-таймзона для `--schedule`; в Linux-образе Docker установлен пакет `tzdata` (см. Dockerfile). |
| `DAILY_BATCH_HOUR`, `DAILY_BATCH_MINUTE` | Время ежедневного пакета в режиме `--schedule`. |
| `LANGUAGE` | Язык интерфейса: `en` или `ru` (по умолчанию). |
| `RUN_BATCH_ON_START` | Выполнить пакет сразу при старте планировщика (`true`/`false`). |

## Docker на Linux

Инструкции в этом разделе рассчитаны **только на хост Linux** с установленными [Docker Engine](https://docs.docker.com/engine/install/) и плагином [Compose](https://docs.docker.com/compose/install/linux/). Docker Desktop на Windows или macOS здесь **не** рассматриваются: пути, права на сокет и примеры ориентированы на обычный Linux-демон Docker.

### Подготовка

```bash
cd /путь/к/ssl_checker
cp .env.example .env
# отредактируйте .env
```

Файлы в репозитории: `Dockerfile`, `docker-compose.yml`. В compose смонтированы `./.env` → `/app/.env` (только чтение) и `./logs` → `/app/logs`.

В `docker-compose.yml` для сервиса задано **`RUN_BATCH_ON_START=false`**: при первом запуске контейнера **немедленная пакетная проверка не выполняется** — только запускается планировщик; первая проверка по расписанию — в **`DAILY_BATCH_HOUR` / `DAILY_BATCH_MINUTE`** (`SCHEDULER_TIMEZONE` из `.env`). Чтобы при старте контейнера сразу выполнить проверку (как при локальном `RUN_BATCH_ON_START=true`), переопределите переменную в compose или удалите блок `environment` и выставьте `RUN_BATCH_ON_START=true` в `.env` (учитывайте приоритет переменных окружения в Compose).

### Сервис по умолчанию (планировщик)

Образ по умолчанию запускает `python main.py --schedule` — ежедневная пакетная проверка по времени из `.env`.

```bash
docker compose up -d --build
```

### Разовый CLI (отдельный контейнер)

Не останавливая сервис с `--schedule`, можно выполнить утилиту одним одноразовым контейнером:

```bash
docker compose run --rm ssl-checker ssl-checker --help
docker compose run --rm ssl-checker ssl-checker --site example.com --json
docker compose run --rm ssl-checker ssl-checker --batch
docker compose run --rm ssl-checker ssl-checker --batch --notify-always
```

### CLI в уже запущенном контейнере

```bash
docker compose exec ssl-checker ssl-checker --site example.com --json
```

### Замечания по среде

- Оконные уведомления Windows в контейнере на Linux **не** используются; для алертов задайте корпоративный HTTP API в `.env` (`SEND_NOTIFICATIONS` и связанные переменные). Правила отправки в API те же, что у **`--batch`**: только при **поводах** по узлам; флаг **`--notify-always`** в фоновом **`--schedule`** не применяется.
- Часовой пояс планировщика задаётся `SCHEDULER_TIMEZONE` в `.env`; в образе установлен `tzdata`.
- Первый прогон проверки в фоновом сервисе из compose — по cron в указанное время; немедленный прогон при старте отключён через `RUN_BATCH_ON_START=false` в compose (см. выше).
